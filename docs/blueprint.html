ต้องถามผู้ให้บริการก่อนซื้อ — 3 ข้อ

1. KVM หรือ container? ต้องการ KVM · Chrome ใช้ user namespace และ seccomp ซึ่ง VPS แบบ container มักปิดไว้ ทำให้ Chrome ไม่ยอมสตาร์ต
2. มีนโยบาย fair-use CPU ไหม? งานนี้กิน CPU 100% ต่อเนื่องครั้งละ 1–3 นาที ทุกงาน ผู้ให้บริการหลายเจ้า throttle หรือระงับเครื่องที่ทำแบบนี้ — นี่คือความเสี่ยงอันดับหนึ่ง
3. /dev/shm ใหญ่เท่าไหร่? Chrome ต้องการ ≥ 1GB ถ้าน้อยกว่านั้นต้องรันด้วย --disable-dev-shm-usage ซึ่งช้าลง

พอร์ต 100 Mbps มีผลต่อการออกแบบ

ดาวน์โหลดได้ราว 12 MB/s — คลิปต้นฉบับ 500MB จะใช้เวลา 40 วินาทีต่อไฟล์ ซึ่งนานกว่าการเรนเดอร์เสียอีก ดังนั้น ขั้น ingest ต้อง normalize ครั้งเดียวแล้วเก็บผลลง R2 และงานเรนเดอร์ต้องดึง ไฟล์ที่ normalize แล้ว (30–60MB) ไม่ใช่ต้นฉบับ ห้ามให้ไฟล์ดิบถูกดาวน์โหลดซ้ำในทุก render

ข้อจำกัดที่ต้องออกแบบรับตั้งแต่แรก

SSE ผ่าน Passenger อาจถูก buffer — บน Plesk shared เราคุม proxy ไม่ได้ ทางถอย polling ทุก 3 วินาที (§08) จึงไม่ใช่ของสำรอง แต่ต้องทดสอบให้ผ่านตั้งแต่วันแรก และถ้า SSE ใช้ไม่ได้จริง ให้ตัดทิ้งแล้วใช้ polling อย่างเดียว อย่าฝืน

API กับ worker อยู่คนละเครื่อง — worker ต้องเข้าถึง MongoDB และ Redis ได้โดยตรง ห้ามให้ worker เรียกกลับมาที่ API เพื่ออัปเดตสถานะ (เพิ่มจุดพังโดยไม่จำเป็น) และต้องล็อก Redis ด้วยรหัสผ่าน + TLS เพราะมันเปิดออกอินเทอร์เน็ตแล้ว

การตัดสินใจสำคัญ

ห้ามเรนเดอร์ใน Next.js API route เด็ดขาด — งาน FFmpeg/Chrome กินเวลาเป็นนาทีและกิน RAM หลัก GB serverless function จะ timeout และคิดเงินตามเวลารัน แยกเป็น worker process ที่กินงานจากคิวตั้งแต่วันแรก ต่อให้ตอน MVP จะรันอยู่บนเครื่องเดียวกันก็ตาม

§05อัลกอริทึมหลัก

5.1 Chunked TTS — หัวใจของความแม่นยำ

ปัญหา: Gemini TTS คืนมาแค่ไฟล์เสียง ไม่บอกว่าคำไหนพูดวินาทีไหน และภาษาไทยไม่มีช่องว่างระหว่างคำ การไปพึ่ง forced aligner ทำให้ซับหลุดและเพิ่ม GPU เข้ามาในระบบ ทางออกคือ ยิง TTS ทีละท่อนตามที่จะโชว์บนจอ แล้ววัดความยาวไฟล์จริง — ปัญหาการ align จึงหายไปทั้งก้อน

กฎการตัดท่อน (Thai chunking)

  • ท่อนละ 2–5 คำ ไม่เกิน 22 อักขระ — เกินกว่านี้อ่านไม่ทันบนจอมือถือ
  • ตัดที่ขอบวลีก่อนเสมอ: หลัง ที่ / แล้ว / เพราะ / แต่ / ก็ และหลังเครื่องหมายวรรคตอน
  • ใช้ pythainlp.word_tokenize(engine="newmm") ผ่าน microservice เล็ก ๆ หรือ wordcut ฝั่ง JS สำหรับตัดคำในท่อน (ใช้กำหนดจังหวะไฮไลต์)
  • ห้ามตัดกลางคำ หรือแยกวรรณยุกต์/สระออกจากพยัญชนะ — ต้องเช็คด้วย grapheme cluster ไม่ใช่ string.length
  • ไฮไลต์คำในท่อน: แบ่งเวลาตามสัดส่วนจำนวนอักขระของแต่ละคำ (ค่าคลาดเคลื่อน < 80ms ตาไม่จับ)

5.2 Duration fitting — ทำให้ภาพพอดีเสียง

ให้  A = ความยาวเสียงพากย์รวม (จาก §5.1)
     V = ความยาวคลิปต้นทางที่ใช้ได้รวม
r = A / V

r ≤ 0.85          → ตัดคลิปให้สั้นลง เลือกช็อตที่ scene score สูงสุด
0.85 < r < 1.15   → ปรับ speed ทีละคลิป (0.92–1.10×) ไม่แตะ pitch เสียงพากย์
r ≥ 1.15          → วนคลิปซ้ำแบบ ping-pong + เติม Ken Burns zoom
r > 1.6           → เตือนผู้ใช้: "สคริปต์ยาวเกินคลิป" + เสนอย่อสคริปต์อัตโนมัติ

ปิดท้ายเสมอ: ยืดเฟรมสุดท้าย 0.4 วิ ให้ CTA อ่านจบ (ห้ามตัดจบพร้อมเสียง)

5.3 การจับคู่ท่อน ↔ ช็อต

MVP ใช้กติกาง่าย ๆ ที่ทำงานได้จริงก่อน: เรียงช็อตตามลำดับที่ผู้ใช้อัปโหลด แล้วแจกให้ท่อนสคริปต์ตามสัดส่วนเวลา โดยบังคับว่า ท่อน hook ต้องได้ช็อตที่ scene score สูงสุด (ค่าความเคลื่อนไหว × ความคมชัด) เพราะ 3 วินาทีแรกชี้เป็นชี้ตาย ส่วน V1.1 ค่อยยกระดับเป็นการจับคู่เชิงความหมายด้วย vision model (ท่อนที่พูดถึง "พับเก็บได้" → ช็อตที่มีการพับ)

กติกาที่ต้องบังคับในโค้ด

  • FlowProducer — งาน render เป็นแม่ที่มีลูกเป็น TTS ทีละท่อน แม่จะเริ่มก็ต่อเมื่อลูกเสร็จครบ (BullMQ จัดการให้)
  • Idempotency — เก็บ idempotencyKey ไว้ใน renders พร้อม unique index กดปุ่มรัว ๆ ต้องไม่ได้งานซ้ำ
  • เครดิตหักตอนสำเร็จ — ตอนสั่งงานให้ "จอง" (hold) ตอน ready ค่อยหักจริง ถ้า failed ให้คืน
  • ทุกงานทำงานใน temp dir ของตัวเอง และลบทิ้งใน finally เสมอ — ดิสก์เต็มคือสาเหตุอันดับหนึ่งที่ระบบวิดีโอล่ม
  • Progress ต้องรายงานจาก stderr ของ FFmpeg (parse out_time_ms) ไม่ใช่เดาเป็นขั้น ๆ
  • Graceful shutdown — รับ SIGTERM แล้วรองานปัจจุบันจบก่อน (สูงสุด 120 วิ) ไม่งั้น deploy ทีงานหายที

  • หน้าพรีวิวห้ามเป็นจอโหลดเปล่า — ระหว่างเรนเดอร์ให้โชว์สถานะเป็นภาษาคน ("กำลังพากย์ท่อนที่ 5 จาก 12") จาก SSE

  • แสดงเครดิตที่จะถูกใช้บนปุ่ม ("สร้างคลิป · 1 เครดิต") ไม่ให้เกิดการหักเงินที่ไม่คาดคิด
  • หน้าพรีวิวคือหน้าเลือกร่าง — โชว์ร่างเป็นกริดเล่นวนอัตโนมัติ ผู้ใช้เลือกตัวที่ชอบแล้วกด "เรนเดอร์ตัวจริง" คำว่าเลน A / เลน B ต้องไม่โผล่ใน UI เลย ผู้ใช้เห็นแค่ ร่าง กับ ตัวจริง และเห็นว่าตัวจริงใช้เวลานานกว่าเพราะซับสวยกว่า
  • ข้อความ error ต้องบอกทางแก้ — "ไฟล์นี้เป็น 4K 60fps เกิน 200MB ระบบย่อให้อัตโนมัติ (ใช้เวลาเพิ่ม ~20 วิ)" ไม่ใช่ "Upload failed"
  • ทุกหน้าใช้งานได้บนมือถือ — ผู้ใช้กลุ่มนี้ทำงานบนมือถือครึ่งหนึ่ง โดยเฉพาะขั้นอัปโหลดและดาวน์โหลด

Definition of Done ของ MVP

  • อัปโหลด 3 คลิป → ได้ไฟล์ MP4 1080×1920 พร้อมโพสต์ ภายใน 60 วินาที

  • สระ/วรรณยุกต์ไทยแสดงถูกต้องทุกสไตล์ ไม่มีตัวอักษรซ้อนหรือกล่องสี่เหลี่ยม
  • งานที่ล้มกลางทางกลับเข้าคิวเองและไม่หักเครดิต
